# 大批量导入、冲突分析和校对状态（2026-10-18）

## 导入事务

保留事务内快照核对、全批次校验和失败回滚。提交期间只整表读取当前课表一次，随后维护本次事务的名称、指纹、课程和时段索引。写入后用单条查询取得数据库中的真实结果，再更新索引；新建课程的实际编号和统一后的名称均以数据库为准。

共享教师、名称和颜色从父课程索引读取，地点及时间保留在各时段中，因此后续记录能立即看到本批次前面已经修改的共享元数据。重复项按课程编号、时段编号保持稳定顺序，整表查询也显式采用相同排序。索引不会跨事务保存。

## 冲突分析

比较阶段复用预计算的规范化名称、实际周次、周次集合和时段指纹。名称查找、重复查找通过索引完成；冲突查询按星期和节次缩小范围，再比较周次交集。来源分组、追加/新建/覆盖模式、排除与独立课程行为保持原规则。

测试保留了旧遍历算法，对随机数据、无效字段、显式目标、分组及三种模式做结果差分，连同冲突的顺序一起核对。密集重叠的冲突输出本身仍可能很多，性能基准使用分散的星期、节次和周次。

## 校对状态

候选记录增加已知待确认字段，区分名称、时间/地点、教师、星期、节次和周次等提示。确认名称时只移除名称的待确认项；名称是唯一问题时退出待校对状态，存在时间分歧时继续显示具体时间提示。

未知来源或旧记录的未分类提示继续保留。字段错误始终独立校验，确认名称不能隐藏缺失星期或无效周次。重新识别保留已人工确认的字段，且不重新开启已确认名称的提示；已确认周次也不再保留旧的“周次缺失”提示。整条记录保存校对后清除旧字段状态和候选。

这些状态属于导入候选，不是数据库实体字段，不需要更改数据库版本或备份格式。

## 基准

### JVM 分析对照

同一进程、同一生成数据，旧遍历与新索引使用相同公共格式化函数，结果逐项相等；不以耗时作测试断言。

| 记录数 | 旧遍历 | 新索引 |
| --- | ---: | ---: |
| 500 | 142 毫秒 | 3 毫秒 |
| 2,000 | 1,074 毫秒 | 8 毫秒 |

这是桌面 JVM 单次测量，不等同于真实手机的页面耗时。

### Android 14 模拟器提交对照

空课表、生成的分散时段。400 条的旧事务与新事务结果完全一致，二者共用新分析算法，以对照整表读取循环的差异。

| 记录数及实现 | 事务内整表读取 | 提交耗时 |
| --- | ---: | ---: |
| 400，旧事务 | 401 次 | 9,017 毫秒 |
| 400，新索引 | 1 次 | 1,236 毫秒 |
| 2,000，新索引 | 1 次 | 12,712 毫秒 |

单条记录查询仍存在；表中不是全部 SQL 的总数。没有运行 2,000 条的旧事务对照。模拟器单次结果受主机和缓存影响。

- 教师分隔表达式复用；每次寻找唯一归属时，候选教师只规范化一次，不再生成全部匹配课程的临时列表。发现第二个匹配即返回歧义。预览与提交共用此逻辑。
